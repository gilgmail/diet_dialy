# 飲食習慣變動與症狀改善關聯：可行性評估

## TL;DR
- **可行但需先補齊事件標記與資料品質**：已有 `food_entries` 與 `daily_symptom_entries` 基礎資料，足以做趨勢分析，但缺「飲食習慣變動事件」標記與餐次營養指標，否則 AI 只能做推測。
- **建議三階段落地**：① 儀表層面蒐集（使用者自報、AI 推測、醫師標記）② SQL/Edge Functions 做 pre/post 差異計算與顯著性評估③ 由既有 AI 分析管線（`refresh-food-analysis` + Admin page）生成自然語言與提醒。
- **風險主要在資料稀疏與誤判**：需要資料可信度、信心分數與提醒使用者補充記錄，並設計 fail-safe（如沒有足夠樣本就提示「資料不足」）。

---

## 背景與產品目標
IBD 使用者常需反覆嘗試飲食調整（減少乳製品、增加可溶性纖維等）以觀察症狀是否改善。現有 AI 食物分析偏向單次餐點或單品風險說明，缺乏「在做出 A 改變後，症狀有沒有改善」的長期回饋。新功能要回答：

1. **習慣層級**：例如「最近 2 週大幅降低辣椒攝取」，系統能標記並追蹤。
2. **症狀趨勢**：比較變動前後的腹痛、腹瀉、血便、Bristol stool、整體健康分數。
3. **可信度評估**：標示樣本天數、症狀變異幅度、潛在干擾因素（藥物、壓力、睡眠）。

## 成功條件與量測
- **資料層**：90% 飲食記錄至少含食物名稱＋餐次時間；70% 症狀日誌有連續 7 天資料。
- **分析層**：能產出 pre/post 差異（平均、變異、趨勢方向）與統計信心（例如 Mann-Whitney U 或簡化的 effect size）。
- **產品層**：使用者能清楚看到「改變 → 結果 → 建議」鏈結，並可分享給醫療團隊。

## 現有資料與缺口

### 食物 / 飲食資料
- ✅ `food_entries`：具 user_id、食物、份量文字、時間戳記，可做餐次聚合。
- ✅ `diet_daily_foods` + `food_analysis_cache`：已有 AI 針對單品產出營養與風險評估，可引用做「此習慣屬於哪類營養變動」。
- ⚠️ 缺少「飲食習慣事件」表（如使用者勾選「開始低 FODMAP」），需新增表格或在 `user_settings` / `user_journal_events` 記錄。
- ⚠️ 無標準化宏量/微量計算：需建 ETL 將 `food_entries` + `diet_daily_foods` 萃取成日/週層級統計（蛋白質、纖維、脂肪、刺激性標籤等）。

### 症狀 / 腸胃資料
- ✅ `daily_symptom_entries`：含 overall_health、腹痛、腹瀉、血便、脹氣、附註、相關食物。
- ✅ `bowel_movement_entries`（007-010 系列 migration）：提供 Bristol stool、血便細節，可合併評估。
- ✅ `symptom_patterns` / `symptom_food_correlations`：可作為存放趨勢與關聯的既有架構。
- ⚠️ 需要缺漏檢查與自動補齊提醒（若 3 天無紀錄，需要 UI 推播，確保分析窗口內資料足夠）。

### AI / Pipeline
- ✅ Edge Function `supabase/functions/refresh-food-analysis` 已建立 AI 呼叫流程，可擴充為「habit change insight」新端點，沿用 queue + cache 模型。
- ⚠️ 目前僅針對單一食物。若要推論「飲食習慣」，需新增 `habit_analysis_cache` 或擴增現有 `food_analysis_cache` schema（例如新增 `analysis_scope = 'habit'`、`time_window` 等欄位）。

## 整體流程建議
1. **定義習慣變動事件**
   - 使用者自訂（UI：在某餐或設定頁標記「開始嘗試 XX 飲食」）。
   - 系統偵測：當 7 天內某類食物攝取量下降 60% 以上、或 AI 偵測關鍵字（如多蔬菜、少乳製品）。
   - 寫入 `diet_change_events`（建議新表 `id, user_id, label, detection_method, start_date, hypothesis_tags`）。

2. **pre/post 視窗建模**
   - 預設使用 ±7 天（可依資料量動態調整）。
   - SQL 產出各症狀平均值、標準差、極值、missing day count。
   - 計算 effect size（(mean_post - mean_pre) / pooled_std）與信心水平（輸出 0-1）。

3. **干擾因素控制**
   - 從 `medications_taken`, `sleep_quality`, `stress_level` 等欄位判斷是否同時計畫其他變因。
   - 若變因過多，回報「可能因其他因素影響，建議繼續觀察」。

4. **AI 解讀與建議**
   - 將 SQL 結果 + 重要事件餵給 AI（類似現有刷新流程）產出自然語言：改善幅度、症狀、風險、下一步建議。
   - 產出 tokens 須控制，可設定摘要模板並讓 AI 只補足 contextual 建議。

5. **前端呈現**
   - 每個事件一張卡片，顯示：變動描述、症狀趨勢（迷你圖）、信心指標、建議行動。
   - 提供「回報結果」按鈕，收集主觀感受以改進模型。

## 風險、成本與緩解
- **資料稀疏 / 不規律**：導致統計噪音。→ 設定最少 5 天資料門檻，並顯示資料充足度條。
- **習慣偵測誤差**：AI 誤判短期波動。→ 允許使用者確認或刪除事件；提供 undo。
- **運算成本**：長期使用者可能有大量窗口。→ 使用物化檢視或 cache 表，僅在資料變動時更新。
- **法規與醫療責任**：需明確聲明非醫療診斷，並允許使用者分享給醫師評估。

## 推薦下一步
1. 與產品／醫師顧問對齊「習慣變動定義」及必備資料欄位，規劃 `diet_change_events` schema。
2. 建立 PoC SQL（以 `food_entries` + `daily_symptom_entries`）跑歷史資料，驗證是否能得出足夠樣本。
3. 決定 AI 端點策略：沿用 `refresh-food-analysis`（加 scope 參數）或新增專用 Edge Function。
4. 規劃提醒與 UI 通知，確保資料持續輸入，否則分析結果將無法產出。

## 從最早記錄到目前的開發瓶頸

### 資料演進回顧
1. **初始階段（000–002 migrations）**：僅有 `diet_daily_foods`、`food_entries` 與少量 `daily_symptom_entries` 欄位，紀錄粒度有限，無法做餐次或症狀趨勢。
2. **症狀與腸胃擴充（001, 006–010）**：加入完整症狀表與大便紀錄，開始能追蹤 Bristol stool、血便狀態，為健康指標建立基礎。
3. **AI 食物分析（20251109 之後）**：新增 `food_analysis_cache`、`food_analysis_refresh_queue`、`find_foods_missing_analysis()` 等，使食物層 AI 計算與重跑流程可控。
4. **目前狀態**：飲食與症狀資料已齊備，但缺乏「飲食習慣事件」與餐次營養聚合，導致 pre/post 分析仍需大量人工推導。

### 現階段瓶頸
- **資料連續性不足**：早期記錄稀疏，導致以「最早資料」為起點時，很多使用者沒有連續 7–14 天的飲食/症狀資料，分析視窗難以成立。
- **事件標記缺失**：即使有歷史紀錄，缺少「何時開始某種飲食策略」的 metadata，只能事後用 AI 推測關鍵字，準確度受限。
- **營養指標仍在計畫中**：`food_entries` 缺乏份量標準化與營養數值，只能依賴 `diet_daily_foods` 中的靜態資料；遇到自由輸入的食物名稱會失準。
- **AI 分析流程分散**：目前 `refresh-food-analysis` 僅處理單食物；若要從早期資料推回「習慣變動」，需要額外的 queue/cache，尚未實作。
- **驗證/迭代成本高**：缺少自動化評估資料集與品質報表，每次調整 prompt/模型都需人工對比。

## AI 分析訓練自動化構想

1. **資料樣本自動蒐集**
   - 建立 `ai_training_dataset` 表：紀錄食物/餐次/習慣事件的輸入（structured data）與期望輸出（人工標記或醫師審核值）。
   - Crons 每日從 `food_analysis_cache`、`daily_symptom_entries` 擷取代表性案例（多族群、不同嚴重度），產生訓練輸入。

2. **Prompt/模型版本控管**
   - 在 queue 中加入 `target_model`/`prompt_version` 欄位，使同一資料可在不同版本下重跑並記錄結果。
   - 建立自動比較腳本，比對「標準答案 vs AI 結果」的差異度，輸出評分。

3. **自動化訓練與回歸測試流程**
   - 透過 CI/CD 或排程腳本，每次更新 prompt/模型設定時：
     1. 從 `ai_training_dataset` 抽樣
     2. 送交目標模型
     3. 蒐集輸出與指標（BLEU、Rouge、或自訂分數）
     4. 未達門檻時自動退回或標記需要人工審查
   - 對於高風險輸出（例如醫療建議）啟用「人工抽樣覆核」，並把覆核結果寫回 dataset。

4. **部署與上線保護**
   - 以 `food_analysis_refresh_queue` 為例，可新增 `dry_run` 模式：先在影子 cache 寫入新模型結果，比對舊版本後再決定是否正式覆蓋。
   - 設定自動監控：若 5% 以上的重跑出現錯誤或 token 超限，即停止批次並通知負責人。

5. **與成本/Token 控制結合**
   - 自動化流程需與前述 token 監控連動，先估算預期 tokens，餘額不足就延後訓練或改用較便宜模型。
   - 針對大型批次訓練可使用離線模型或蒐集輸入後批次送出，減少即時 API 壓力。

> 自動化目標不是完全取消人工，而是建立「資料 → 訓練 → 評估 → 上線」的流水線，讓 prompt/模型迭代更有節奏、可重複、可追蹤。

## 實務操作模擬與資料評估

### 每人輸入時間（假設日常使用）
| 角色 | 動作 | 頻率 | 單次耗時估算 | 每日合計 |
| --- | --- | --- | --- | --- |
| 患者 | 記錄 3 餐主要食物（文字 + 份量 + 照片可選） | 3 次/日 | 1–1.5 分鐘 | 3–4.5 分鐘 |
| 患者 | 每日晚間填寫症狀／睡眠／運動問卷 | 1 次/日 | 2–3 分鐘 | 2–3 分鐘 |
| 患者 | 大便紀錄（平均 1 次/日） | 1 次/日 | 1 分鐘 | 1 分鐘 |
| 患者 | 習慣事件標記（例如開始低 FODMAP） | 不定期 | 2 分鐘 | 月平均 <0.1 分鐘 |
| 醫師/照護者 | 審閱週報 + 備註 | 1 次/週 | 5–7 分鐘 | 約 1 分鐘/日 |
> 以此估算，患者每日約花 6–8 分鐘即可提供完整資料；若可導入語音/捷徑或照片辨識，可降至 4–5 分鐘。

### 資料完備性檢查點
- **飲食覆蓋率**：計算每日是否至少有早餐/午餐/晚餐紀錄。目標 ≥90% 的活躍日具備 ≥2 餐紀錄。
- **症狀與大便連續性**：連續 7 日紀錄比例，若缺漏>2 日觸發提醒。
- **習慣事件標記率**：對於系統偵測之用戶，至少 70% 需獲得使用者確認或否認，避免 ghost event。
- **補充資料**：睡眠/運動輸入率、藥物/壓力記錄，同時影響分析可信度；可在報表顯示資料充足度條。

### 分析精準度預期
- **單食物 AI 分析**：依賴 AI 模型 + `diet_daily_foods` metadata，輸出風險/建議。品質取決於 prompt 與資料齊全度，可達 80–90% 一致（以人工審核為準）。
- **每日/單餐分析**：目前以規則 + AI 摘要混合，若營養聚合可靠，精準度受限於份量估算。可透過資料充足度 >80% 時才啟用建議。
- **pre/post 習慣分析**：需至少 5 日資料於前/後視窗，樣本不足時標記為低信心。引入 effect size 與信心指標以透明呈現。

### 目前可進行的分析
- 單一食物風險/營養評估（`food_analysis_cache`）
- 使用者近況的症狀概覽（overall health + Bristol +血便指標）
- 大便紀錄趨勢（利用 007–010 migrations 資料）
- 基本飲食覆蓋率、資料缺漏提醒（藉由 SQL 報表即可）

### 尚未納入的關鍵資料
- 藥物劑量與用藥變更時間點（目前僅有 `medications_taken` JSON 記錄）
- 體重、身體組成、炎症指標（一旦醫療院所提供可成為重要輸入）
- 長期壓力/情緒追蹤（僅有單日 `mood_score`，缺乏觸發事件）
- 睡眠時數、運動強度的客觀數據（需穿戴裝置或 API）
- 水分/補給品攝取、藥物遵從率（現有欄位但填寫意願低）

### 最小化分析開展方式（MVP）
1. **資料門檻**：要求使用者至少連續 5 天記錄食物 + 症狀 + 大便，並於 UI 顯示進度條鼓勵達標。
2. **規則優先**：先使用規則/統計摘要（ex: 高頻刺激食物＋症狀升高）產生可驗證的 insight，再由 AI 產出文字敘述，確保結果可追溯。
3. **單事件試點**：先針對「減少辛辣 / 減少乳品」等常見習慣搭配 pre/post 視窗，產出少量高信心卡片，收集使用者與醫師回饋。
4. **逐步擴充資料**：當睡眠/運動記錄達 60% 以上時，再開啟多變量關聯分析，避免空洞結果。
5. **回饋機制**：在每張分析卡片提供「有幫助 / 未察覺」選項，持續蒐集實際準確度並更新訓練資料。

# 專案開發指南

## 專案結構與模組組織
- 所有執行時程式碼放在 `src/`；導航位於 `src/app/RootNavigator`，功能領域（認證、儀表板、飲食日記、症狀日記）位於 `src/features` 下。
- 將客戶端、狀態儲存和類型共享於 `src/shared`，並在 `src/theme` 中編寫設計標記。
- 在 `App.tsx` 和 `index.ts` 中初始化應用程式。將測試放在文件旁邊或 `src/__tests__/` 下，媒體資源存放於 `assets/`。
- 原生平台配置位於 `ios/`；避免在其他地方重複配置。

## 建置、測試和開發指令
- `npm start` 啟動 Expo 開發伺服器並支援即時重載。
- `npm run android` / `npm run ios` 透過 Expo Run 在連接的設備或模擬器上建置和運行專案。
- `npm run web` 在 Expo 網頁執行環境中驗證響應式佈局。
- `npx expo test` 執行 Jest 測試套件；在本機開發時可加上 `--watch`。

## 編碼風格與命名規範
- 使用現代 TypeScript 編寫功能性 React 元件，採用兩空格縮排，不使用分號。
- 元件/畫面使用 PascalCase 命名，hooks/工具函式使用 camelCase，透過 `@/shared/...` 匯入重用邏輯而非深層相對路徑。
- 將樣式與元件放在一起，從 `src/theme` 引用設計標記；優先使用 hooks 進行狀態管理。
- 提交前執行 `npx prettier --check "src/**/*.{ts,tsx}"` 和 `npx eslint "src/**/*.{ts,tsx}"`。

## 測試指南
- 測試使用 Jest 和 `@testing-library/react-native`，檔名以 `.test.ts` 或 `.test.tsx` 結尾。
- 目標達成 ≥80% 語句覆蓋率，強調使用者流程而非實作細節的斷言。
- 當快照能捕捉有意義的 UI 變更時可接受；審查差異後再批准。

## 提交與 Pull Request 指南
- 使用慣例式提交（`feat:`、`fix:`、`chore:` 等），每個提交專注於單一關注點。
- Pull request 應總結變更、連結相關議題/任務 ID、附上 UI 更新的截圖，並貼上最新的測試輸出。
- 在合併前請求功能區域負責人審查並確認 Expo 建置檢查通過。

## 安全性與配置建議
- Expo 從 `app.json` 讀取配置；將機密資訊保存在未追蹤的 `.env` 檔案中，並透過環境輔助工具載入。
- 透過 `src/shared/api` 中的型別化客戶端引入後端整合，並在相應的功能儲存中協調狀態轉換以維持可預測的資料流。

## 行動應用程式策略

### 我們的行動應用程式執行的任務

**主要任務（功能性）**：
使 IBD/IBS 患者能夠在事件發生時立即捕捉即時症狀和飲食資料，無摩擦、無延遲。

**情感任務**：
減少因擔心忘記症狀或食物而在就診間產生的焦慮。提供健康資料安全記錄並將帶來洞察的信心。

**社交任務**：
透過從行動裝置捕獲的資料生成結構化、專業的報告，使患者能夠有效地與醫療提供者溝通。

**為什麼行動優先很重要**：
- 症狀不可預測地發生；行動裝置確保立即捕獲
- 飲食記錄需要在用餐時進行以確保準確性
- 照片提供文字無法捕捉的視覺背景（份量大小、成分）
- 通知能及時提醒，無需使用者記住

### 競爭優勢與差異化

**獨特價值主張**：

1. **AI 驅動的行動指導**（vs. 僅網頁版 AI 分析）
   - 基於膳食組合的即時症狀嚴重程度預測
   - 在症狀惡化前主動發出發作警報
   - 根據當前腸道狀態提供個人化膳食建議

2. **離線優先的醫療可靠性**
   - 無需網路即可完整功能（在醫院就診時至關重要）
   - 連接恢復時自動同步
   - 冗餘本地儲存防止資料遺失

3. **語音與照片捕獲**
   - 語音轉文字症狀記錄（在不適時免持操作）
   - 基於照片的食物識別與 AI 營養分析
   - 比任何競爭對手更快的資料輸入（目標：<30 秒/條目）

4. **台灣/香港市場專注**
   - 亞洲食物資料庫（20,000+ 項目）含繁體中文
   - 與本地醫療系統整合（健保、醫管局）
   - 對傳統醫學 + 西醫治療的文化理解

**可防禦的護城河**：
- **資料網路效應**：更多使用者 → 更好的 AI 預測 → 更準確的洞察
- **醫療提供者關係**：直接與醫院/診所整合
- **法規合規**：FDA/PMDA 審批流程形成進入障礙

## 提升的醫療應用程式標準

### 為什麼醫療應用程式需要更高的標準

**不對稱風險**：與消費者應用程式不同，醫療應用程式失敗可能導致患者受傷害：
- 症狀資料不正確 → 錯誤的治療決策
- 飲食記錄遺失 → 錯過觸發因素識別
- 發作期間應用程式崩潰 → 延遲干預

### 增強的測試要求

**測試覆蓋率：95%（vs. 消費者應用程式的 80%）**

**優先測試區域**：
1. **關鍵路徑覆蓋：100%**
   - 症狀輸入建立和儲存
   - 飲食日記資料捕獲和同步
   - 離線模式和同步恢復
   - 使用者認證和會話管理

2. **資料完整性測試**
   - 症狀嚴重程度一致性檢查
   - 時間戳準確性驗證
   - 同步衝突解決
   - 資料遺失防護驗證

3. **故障模式測試**
   - 同步期間網路中斷
   - 資料輸入期間應用程式終止
   - 裝置儲存已滿場景
   - 並發修改衝突

**測試指令**：

### 資料完整性驗證

**冗餘儲存策略**：
```typescript
// 每個關鍵醫療資料點儲存在 3 個位置
interface DataIntegrityLayer {
  local: AsyncStorage;        // 立即持久化
  queue: SyncQueue;            // 待上傳
  remote: SupabaseClient;      // 雲端備份
}

// 每次讀取時驗證
const verifyDataIntegrity = async (entryId: string) => {
  const local = await AsyncStorage.getItem(entryId);
  const remote = await supabase.from('symptoms').select().eq('id', entryId);

  if (local !== remote) {
    // 觸發衝突解決
    await resolveConflict(local, remote);
  }
};
```

**審計追蹤要求**：
- 每個症狀條目記錄裝置 ID、時間戳、應用程式版本
- 追蹤修改歷史（誰、什麼、何時）
- 使用者可清楚看到同步狀態
- 具備醫療記錄合規的匯出能力

### 離線優先架構文件

**核心原則**：
1. **本地優先**：所有寫入操作立即成功到本地儲存
2. **背景同步**：網路操作絕不阻塞使用者互動
3. **衝突解決**：最後寫入獲勝，關鍵衝突通知使用者
4. **資料一致性**：最終一致性，關鍵醫療資料強一致性

**架構圖**：
```
使用者操作 → 本地 AsyncStorage → 同步佇列 → Supabase 雲端
   ↓              ↓（即時）          ↓（背景）      ↓
UI 更新      樂觀 UI           失敗重試      權威資料
（立即）     （響應式）        （彈性）     （持久）
```

**實作檢查清單**：
- [ ] 具備醫療資料加密的 AsyncStorage 包裝器
- [ ] 具備指數退避重試邏輯的同步佇列
- [ ] 衝突檢測和面向使用者的解決 UI
- [ ] 使用 Expo Background Fetch 的背景同步
- [ ] 網路狀態監控和使用者回饋
- [ ] 應用程式前景時的資料一致性驗證

**離線測試協議**：

## 醫療應用程式合規與安全

### 法規考量

**FDA 分類**（美國市場）：
- 目前：行動醫療應用程式（MMA）- 可能為第 I 類（最低風險）
- 如果添加診斷功能 → 可能需要第 II 類（510(k) 許可）
- 策略：維持為「生活方式追蹤」以避免嚴格監管

**PMDA**（日本市場）：
- 如聲稱醫療效益，需註冊為「程式醫療器材」
- 治療聲明需要臨床資料

**台灣/香港**：
- 遵循當地醫療器材軟體法規
- 醫療資料的資料駐留要求

### 資料隱私與安全

**GDPR/PDPA 合規**：
- [ ] 訪問權（使用者資料匯出）
- [ ] 刪除權（完整刪除）
- [ ] 資料最小化（僅收集必要）
- [ ] 靜態和傳輸中加密
- [ ] 資料訪問的審計記錄

**HIPAA 準備**（如與美國提供者整合）：

- [ ] 加密儲存（AES-256）

## 效能與無障礙標準

### 效能目標（醫療應用程式要求）

**冷啟動**：<2 秒（vs. 消費者應用程式的 3-5 秒）
- 對於發作期間立即捕捉症狀至關重要

**可互動時間**：<3 秒
- 使用者需要立即訪問記錄功能

**幀率**：持續 60 FPS
- 即使在疼痛發作期間也能確保流暢體驗

**記憶體使用**：<150MB
- 必須在舊裝置上運行（患者可能不經常升級）

**電池消耗**：每小時活躍使用 <5%
- 全天症狀監控不應耗盡電池

- [ ] 文字最小 4.5:1 對比度
